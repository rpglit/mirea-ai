# GAP-анализ (часть 1: backend и терминология)

Составлено: compatibility-agent (часть 1), 08.10.2026.
Вход: `docs/MATERIALS_ANALYSIS.md` (§3 каталог 71 задачи, §5 глоссарий, §8 эталоны),
код `backend/src/petrinet/`, `backend/tests/`, `frontend/`.
Метод: приложение поднято (`sudo docker compose up -d --build app`, `GET /healthz` → `{"status":"ok"}`),
проверка фактических возможностей — только curl (код не изменялся). Все результаты §5
сняты с работающего контейнера (http://localhost:8080) 08.10.2026.

Доступные эндпоинты (полный список, `api/routes.py`):
`POST /parse` (text|json|form), `POST /graph` (auto|bounded|coverability), `POST /properties`,
`POST /fire` (fire|undo|reset), `POST /goto`, `GET /state/{sid}`, `GET /sessions`,
`GET /sessions/{sid}`, `GET /sessions/{sid}/graph`, `DELETE /sessions/{sid}`,
`GET /sessions/{sid}/export/report`, `GET /sessions/{sid}/export/markings`, `GET /healthz`.
Каноническая модель сети — ровно 5 полей (`schema.json`, `additionalProperties: false`):
`places, transitions, inputs, outputs, initial_marking` (целочисленные веса дуг).

## 3. Отсутствующие возможности (с привязкой к TASK-ам)

   (ключей: approximation, bounded, dead_transitions, deadlock_free, deadlocks,
   global_k, home_state, liveness, per_place_k, safe, stats). Структурная проверка
   (Σвходов(t)=Σвыходов(t) для всех t) тривиальна на текущей модели.
   Затрагивает: PN-04, PN-08, PN-09, PN-19, PN-21, PN-28, PN-29, PN-31 (8 задач).
2. **Минимальная маркировка µmin** (М6: покомпонентный максимум требований I(tj)) —
   нет эндпоинта и функции. Затрагивает: PN-07, PN-09, PN-19.
3. **Матричное представление W−/W+/W, v(σ), µ′=µ+W·v(σ)** (М7) — `/matrices`
   отсутствует (404/405); `/parse` отдаёт только словесные карты inputs/outputs.
   Затрагивает: PN-18 (явный пункт), PN-35 (ядро метода), PN-17 (метод).
4. **Приоритеты Pr t** (М8) — поля нет в schema.json (additionalProperties=false),
   семантики конфликта нет. Затрагивает: PN-10, PN-30.
5. **Временные сети / задержки τ** (М9) — поля задержек на дугах нет.
   Затрагивает: PN-15 (вариант с задержками), PN-32.

   только input/output, parser.py:255). Затрагивает: PN-33.

   метки только целые. Затрагивает: PN-36, PN-37.
8. **Параллельное срабатывание** (принцип максимального параллелизма, конфликты) —
   `/fire` принимает ровно один переход. Затрагивает: PN-07 (часть), терминология §5.1.
9. **Синтез/модификация сети** (М10 «достроить») — нет редактирования существующей

**Шкала живости L0–L4 (приложение) vs бинарная классификация методички (отдельно):**
- Приложение (`properties.py:12,48–54`, ADR-0004): попереходная шкала — L0 «dead»
  (переход не возникает ни в одной достижимой маркировке), L1 «occurs» (возникает
  хотя бы раз), L3 «cycle-with-t» (лежит на достижимом цикле), L4 «live» (из любой
  достижимой маркировки можно дойти до срабатывания t); L2 сознательно не выдаётся
  (на конечном графе L2≡L3). Уровень сети = min по переходам. Проверено на
  эталонной сети: фактический уровень **L1** (все t1–t5 возникают, но ни один не
  лежит на достижимом цикле — независимо пересчитано через SCC; сумма меток не
  консервативна, циклов возврата нет).
- Методичка (§5.1): три класса сети — «живая» (из любой текущей позиции любой
  переход может сработать) ⇔ level=L4; «тупиковая» (существует достижимая
  маркировка без разрешённых переходов) ⇔ deadlocks≠∅; «частичнотупиковая»
  (часть переходов перестаёт срабатывать, часть работает бесконечно) — прямого
  соответствия нет; ближайшие данные: level<L4 + non-empty dead_transitions +
  наличие маркировок с живыми переходами (вывод вручную по графу).
- Замечание по качеству кода: docstring `properties.py:190–193,338–341` содержит
  устаревший якорь «liveness level L3» для smoke-сети, тогда как фактический
  (и зафиксированный в DECISIONS_LOG.md:35–37,150–153) ответ — L1; поведение
  корректно, docstring не обновлён.
